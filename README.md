\# uv docs assistant



A retrieval-augmented generation (RAG) system that answers questions about the \[uv](https://docs.astral.sh/uv/) documentation. Answers cite their source files, and the system refuses to answer when the documentation does not contain the answer.



\*\*Live demo:\*\* https://rag-docs-assistant-m7cvczp73hhuyyywy7lbku.streamlit.app/ (the app sleeps when idle; the first load can take a minute)



!\[Demo](docs/demo.png)



\## Why this project



Most RAG demos stop at "chat with a PDF". This one measures whether the system works: a 54-question evaluation set, retrieval and answer metrics, and an experiment comparing chunk sizes and retrieval depth on quality, latency and cost.



uv was chosen deliberately: it is recent and changes often, so the model cannot answer everything from memory, and the effect of retrieval is measurable.



\## Architecture



```mermaid

flowchart LR

&#x20;   A\[uv docs .md files] --> B\[Chunking<br/>150 words, 25 overlap]

&#x20;   B --> C\[Embeddings<br/>text-embedding-3-small]

&#x20;   C --> D\[(Chroma<br/>vector store)]

&#x20;   Q\[Question] --> E\[Embed question]

&#x20;   E --> D

&#x20;   D -->|top 5 chunks| F{Distance<br/>below 0.6?}

&#x20;   F -->|no| G\[Refuse: I don't know]

&#x20;   F -->|yes| H\[LLM answers using only the context, with citations]

&#x20;   H --> I\[Answer and sources]

```



Two layers protect against hallucination:

1\. \*\*Distance filter:\*\* if no retrieved chunk is close enough, the model is not even called.

2\. \*\*Prompt:\*\* the model must answer only from the context, cite the source file, and say "I don't know" otherwise.



\## Evaluation



The evaluation set has 54 questions: 46 answerable (39 generated from random chunks and reviewed, 7 written by hand in a casual style) and 8 unanswerable (5 about uv topics that are not in the docs, 3 off-topic).



\- \*\*Hit@k:\*\* the correct file appears among the k retrieved chunks.

\- \*\*Correctness:\*\* an LLM judge compares the answer to a reference answer.

\- \*\*Faithfulness:\*\* an LLM judge checks that every claim is supported by the retrieved context.



\### Experiment: chunk size and k



| Config | Hit | Correct | Faithful | False refusals | Correct refusals | Latency | Cost per 1000 questions |

|---|---|---|---|---|---|---|---|

| 150w, k=3 | 91.3% | 84.8% | 100.0% | 3 | 8/8 | 2.23 s | $0.171 |

| \*\*150w, k=5\*\* | \*\*93.5%\*\* | \*\*91.3%\*\* | \*\*97.8%\*\* | \*\*1\*\* | \*\*8/8\*\* | \*\*2.35 s\*\* | \*\*$0.251\*\* |

| 300w, k=3 | 91.3% | 87.0% | 100.0% | 1 | 8/8 | 2.45 s | $0.281 |

| 300w, k=5 | 93.5% | 87.0% | 100.0% | 1 | 8/8 | 2.61 s | $0.419 |

| 500w, k=3 | 87.0% | 84.8% | 97.6% | 4 | 8/8 | 2.38 s | $0.407 |

| 500w, k=5 | 93.5% | 93.5% | 97.8% | 1 | 8/8 | 2.38 s | $0.636 |



\*\*Chosen: 150 words, k=5.\*\* Retrieval saturated at 93.5% for every k=5 configuration. The 500w/k=5 setup scored one question higher on correctness but costs 2.5x more, a difference well within noise on 46 questions, so I picked the best quality-to-cost ratio.



\### Findings



\- \*\*A distance threshold alone is not enough to refuse.\*\* Off-topic questions (distance 0.79 to 0.90) were filtered, but questions about uv topics missing from the docs (Bazel, AWS Lambda, JFrog, Dependabot, Coiled) had distances of 0.42 to 0.57. Embeddings measure topical similarity, not whether the answer exists. Those 5 refusals come from the prompt instruction, not from the filter.

\- \*\*Faithful is not the same as correct.\*\* A few wrong answers were fully supported by the retrieved context, because the right chunk was never retrieved (for example, answering with the system-level config path instead of the user-level one).

\- \*\*Latency barely changes with prompt size\*\* (2.2 to 2.6 s), because it is dominated by API round trips, while cost scales with tokens sent.



\## Limitations



\- The evaluation set is small: one question is about 2 percentage points, so differences of 1 to 2 questions are noise.

\- Most questions were generated by an LLM from the same chunks the system retrieves, which makes them easier than real user questions. I added 7 hand-written questions to partly compensate.

\- The judge and the answering model are the same model, which can make grading lenient.

\- Some ground-truth labels were too strict (several files can answer the same question), so a few "misses" are label problems, not system errors.



\## Stack



Python, OpenAI API (embeddings and chat), Chroma, Streamlit, FastAPI, pandas, Docker.



\## Project structure



| File | Purpose |

|---|---|

| `chunking.py` | Reads the docs and splits them into overlapping chunks |

| `ingest.py` | Embeds chunks and stores them in Chroma |

| `search.py` | Retrieves the most similar chunks for a question |

| `rag.py` | Builds the prompt and generates a cited answer |

| `app.py` | Streamlit interface |

| `api.py` | FastAPI `/ask` endpoint |

| `bootstrap.py` | Builds the index on first start |

| `generate\_questions.py`, `finalize\_questions.py` | Build the evaluation set |

| `eval\_retrieval.py`, `eval\_answers.py`, `experiments.py` | Evaluation and experiments |

| `eval/questions.json` | The 54 evaluation questions |

| `Dockerfile` | Container image |



\## Run locally



```bash

python -m venv venv

venv\\Scripts\\Activate.ps1        # Windows PowerShell; on Mac/Linux: source venv/bin/activate

pip install -r requirements.txt

```



Create a `.env` file with `OPENAI\_API\_KEY=sk-...`, then:



```bash

python ingest.py                 # builds the vector index

streamlit run app.py             # web interface

uvicorn api:app --reload         # optional: REST API on /docs

python eval\_retrieval.py         # retrieval metrics

python eval\_answers.py           # answer metrics (LLM judge)

```



With Docker:



```bash

docker build -t uv-docs-assistant .

docker run --rm -p 7860:7860 --env-file .env uv-docs-assistant

```
